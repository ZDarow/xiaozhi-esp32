## 1. Находки P0

### P0-1. `std::stoi` на данных от сервера при отключённых исключениях → abort

| Поле | Значение |
|------|----------|
| Места | `main/ota.cc:435`, `main/protocols/mqtt_protocol.cc:154`, `main/audio/audio_debugger.cc:25` |
| Ввод | `firmware.version` и `endpoint` из JSON-ответа OTA-сервера |
| Доказательство | `sdkconfig.defaults:2` → `CONFIG_COMPILER_CXX_EXCEPTIONS=n` |
| Симптом | `std::stoi` бросает `std::invalid_argument`/`std::out_of_range`; при `-fno-exceptions` путь завершается `_GLIBCXX_THROW_OR_ABORT` → `abort()` → panic → перезагрузка |

Цепочка данных: `Ota::CheckVersion()` (`main/ota.cc:145-273`) разбирает ответ сервера и
сохраняет строки в поля; `IsNewVersionAvailable()` → `ParseVersion()` вызывает
`std::stoi(segment)` на каждом сегменте после split по `.`. Значение `"1.x"`, `"1..2"`,
`"latest"` или число длиннее `int` приводят к панике. Второе место: `mqtt_protocol.cc:154`
разбирает порт из `endpoint`, который заполняется тем же ответом OTA-сервера
(`main/ota.cc:176-190`, `Settings("mqtt")`).

**Критерий проверки:** хост-тест или проверка на железе с ответом сервера
`{"firmware":{"version":"1.x","url":"https://example/1.bin"}}` не вызывает перезагрузку;
в лог пишется `ESP_LOGW` о некорректной версии и `has_new_version_` остаётся `false`.
Замена `std::stoi` на `strtol` с проверкой `errno`/`endptr` во всех трёх местах.

### P0-2. Серверные ключи NVS → `ESP_ERROR_CHECK` → panic

| Поле | Значение |
|------|----------|
| Места | `main/settings.cc:53` (`nvs_set_str`), `main/settings.cc:74` (`nvs_set_int`) |
| Ввод | имена ключей из JSON без какой-либо фильтрации |
| Доказательство | `main/ota.cc:180-190` и `:202-212` — `cJSON_ArrayForEach` пишет любой ключ объекта `mqtt`/`websocket` |
| Симптом | `ESP_ERROR_CHECK` → `_esp_error_check_failed()` → panic |

`NVS_KEY_NAME_MAX_SIZE = 16` (`components/nvs_flash/include/nvs.h:60`), то есть максимум
15 символов; `nvs_set_str` возвращает `ESP_ERR_INVALID_ARG` для более длинного ключа.
Идентичный исход даёт заполнение namespace (`ESP_ERR_NVS_NOT_ENOUGH_SPACE` /
`ESP_ERR_NVS_NO_FREE_PAGES`) при множестве произвольных ключей из ответа.

**Критерий проверки:** ответ сервера с ключом длиной 20 символов и с 200 ключами
не приводит к перезагрузке; в лог — `ESP_LOGE` о недопустимом ключе. Нужны фильтрация
имён по белому списку и замена `ESP_ERROR_CHECK` на проверку возвращаемого `esp_err_t`
в `Settings::SetString`/`SetInt`.

## 2. Находки P1

### P1-3. Схема URL образа не проверяется, подписи нет
`main/ota.cc:249-252` принимает `firmware.url` без проверки схемы; `Upgrade()`
(`main/ota.cc:296-421`) пишет образ в раздел и переключает загрузку без проверки
подписи. `esp_ota_end` проверяет только целостность (SHA-256 сегментов), не
подлинность. Следствие: компромеция или подмена OTA-эндпоинта даёт подмену прошивки
и конфигурации разделов `mqtt`/`websocket` (см. P0-2). Критерий: не-`https` URL →
отказ; отдельная опция «подпись обязательна»; при выключенной подписи — явная запись в лог.

### P1-4. Активационный HMAC и серийный номер печатаются в лог
`main/ota.cc:493` — `ESP_LOGI(TAG, "Activation payload: %s", json.c_str())`, в payload
входят `serial_number` и `hmac` (`main/ota.cc:483-486`); `main/ota.cc:80` — печать
`Serial-Number`. Критерий: значение HMAC маскируется (`hmac=ab****yz`), серийный номер
не выводится целиком.

### P1-5. Сырые MCP-сообщения уходят в лог целиком
`main/mcp_server.cc:333` печатает `message.c_str()` при ошибке парсинга; входящее
сообщение не ограничено по длине на уровне `McpServer`.
Уточнение к плану: `max_length` в `main/mcp_server.h:115-160` применяется к аргументам
инструментов при их формировании, а не к входящим сообщениям — утверждение «в `mcp_server`
уже есть `max_length`» в плане неточно. Критерий: в лог уходит длина и первые N байт.

### P1-6. Китайский сервис в шаблонах issues и поддержке
Упоминания `https://xiaozhi.me/`:
`.github/ISSUE_TEMPLATE/01_build_flash_bug.yml:9`,
`02_runtime_bug.yml:9` и `:42`,
`03_feature_request.yml:9`, `05_technical_question.yml:9`,
`config.yml:7`, `.github/SUPPORT.md:49`.
Поддержка переведена на `support@xiaozhi.ru`, но сайт остался китайским.
Критерий: `grep -rn "xiaozhi.me" .github/` пусто.

### P1-7. Сторонних зависимостей 19 из 62, а не 3
`main/idf_component.yml`: кроме `78/*` и `ZDarow/*` компоненты приходят из
`waveshare/*` (4), `m5stack/*` (2), `esphome/esp-hub75`, `txp666/otto-emoji-gif-component`,
`wvirgil123/sscma_client`, `tny-robotics/sh1106-esp-idf`, `espfriends/servo_dog_ctrl`,
`kevincoooool/esp_lcd_st7102`, `cube32esp/xpowerslib`. Все тянутся с `github.com`.
Требуется зеркало для каждого источника, а утверждение в `AGENTS.md` о «78/* и ZDarow/*»
надо расширить. Критерий: инвентаризация зеркал покрывает все 19 источников.
