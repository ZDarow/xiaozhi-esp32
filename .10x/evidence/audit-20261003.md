## 1. Находки P0

### P0-1. `std::stoi` на данных от сервера при отключённых исключениях → abort

| Поле | Значение |
|------|----------|
| Места | `main/ota.cc:435`, `main/protocols/mqtt_protocol.cc:154`, `main/audio/audio_debugger.cc:25` |
| Ввод | `firmware.version` и `endpoint` из JSON-ответа OTA-сервера |
| Доказательство | `sdkconfig.defaults:2` → `CONFIG_COMPILER_CXX_EXCEPTIONS=n` |
| Симптом | `std::stoi` бросает `std::invalid_argument`/`std::out_of_range`; при `-fno-exceptions` путь завершается `_GLIBCXX_THROW_OR_ABORT` → `abort()` → panic → перезагрузка |

Цепочка данных: `Ota::CheckVersion()` (`main/ota.cc:145-273`) разбирает ответ сервера и
сохраняет строки в поля; `IsNewVersionAvailable()` → `ParseVersion()` вызывает
`std::stoi(segment)` на каждом сегменте после split по `.`. Значение `"1.x"`, `"1..2"`,
`"latest"` или число длиннее `int` приводят к панике. Второе место: `mqtt_protocol.cc:154`
разбирает порт из `endpoint`, который заполняется тем же ответом OTA-сервера
(`main/ota.cc:176-190`, `Settings("mqtt")`).

**Критерий проверки:** хост-тест или проверка на железе с ответом сервера
`{"firmware":{"version":"1.x","url":"https://example/1.bin"}}` не вызывает перезагрузку;
в лог пишется `ESP_LOGW` о некорректной версии и `has_new_version_` остаётся `false`.
Замена `std::stoi` на `strtol` с проверкой `errno`/`endptr` во всех трёх местах.

**Закрыто 03.10.2026 (коммит `73935ee`).** Добавлен `ParseInt` в `main/string_utils.h`:
только десятичная запись с необязательным знаком, проверка диапазона, `strtol` + `errno`.
Применён в `Ota::ParseVersion`, `MqttProtocol::StartMqttClient` и `AudioDebugger`.
Хост-тест проверяет 10 некорректных версий и 20 вариантов порта/границ диапазона.

### P0-2. Серверные ключи NVS → `ESP_ERROR_CHECK` → panic

| Поле | Значение |
|------|----------|
| Места | `main/settings.cc:53` (`nvs_set_str`), `main/settings.cc:74` (`nvs_set_int`) |
| Ввод | имена ключей из JSON без какой-либо фильтрации |
| Доказательство | `main/ota.cc:180-190` и `:202-212` — `cJSON_ArrayForEach` пишет любой ключ объекта `mqtt`/`websocket` |
| Симптом | `ESP_ERROR_CHECK` → `_esp_error_check_failed()` → panic |

`NVS_KEY_NAME_MAX_SIZE = 16` (`components/nvs_flash/include/nvs.h:60`), то есть максимум
15 символов; `nvs_set_str` возвращает `ESP_ERR_INVALID_ARG` для более длинного ключа.
Идентичный исход даёт заполнение namespace (`ESP_ERR_NVS_NOT_ENOUGH_SPACE` /
`ESP_ERR_NVS_NO_FREE_PAGES`) при множестве произвольных ключей из ответа.

**Критерий проверки:** ответ сервера с ключом длиной 20 символов и с 200 ключами
не приводит к перезагрузке; в лог — `ESP_LOGE` о недопустимом ключе. Нужны фильтрация
имён по белому списку и замена `ESP_ERROR_CHECK` на проверку возвращаемого `esp_err_t`
в `Settings::SetString`/`SetInt`.

**Закрыто 03.10.2026 (коммит `73935ee`).** `main/ota.cc` фильтрует ключи секций `mqtt`
и `websocket` по белому списку (`kAllowedMqttKeys`, `kAllowedWebsocketKeys`); неизвестные
ключи логируются и игнорируются. `Settings` больше не использует `ESP_ERROR_CHECK`
на путях записи, проверяет длину ключа по `NVS_KEY_NAME_MAX_SIZE`, пустой ключ и NUL-байт,
а сеттеры возвращают `bool`. Регрессии закрыты `scripts/tests/test_server_input_hardening.py`.

## 2. Находки P1

### P1-3. Схема URL образа не проверяется, подписи нет
`main/ota.cc:249-252` принимает `firmware.url` без проверки схемы; `Upgrade()`
(`main/ota.cc:296-421`) пишет образ в раздел и переключает загрузку без проверки
подписи. `esp_ota_end` проверяет только целостность (SHA-256 сегментов), не
подлинность. Следствие: компромеция или подмена OTA-эндпоинта даёт подмену прошивки
и конфигурации разделов `mqtt`/`websocket` (см. P0-2). Критерий: не-`https` URL →
отказ; отдельная опция «подпись обязательна»; при выключенной подписи — явная запись в лог.

### P1-4. Активационный HMAC и серийный номер печатаются в лог
`main/ota.cc:493` — `ESP_LOGI(TAG, "Activation payload: %s", json.c_str())`, в payload
входят `serial_number` и `hmac` (`main/ota.cc:483-486`); `main/ota.cc:80` — печать
`Serial-Number`. Критерий: значение HMAC маскируется (`hmac=ab****yz`), серийный номер
не выводится целиком.

**Закрыто 04.10.2026.** В анонимный namespace `main/ota.cc` добавлен `MaskSecret()`:
значения короче 9 символов заменяются на `********`, у остальных остаются первые и
последние четыре символа. `Ota::SetupHttp` печатает маскированный `Serial-Number`,
`Ota::GetActivationPayload` больше не выводит тело payload — в лог уходят только длина,
алгоритм и маскированный HMAC. Регрессии закрыты двумя тестами в
`scripts/tests/test_server_input_hardening.py`: `test_mask_secret_hides_middle` (логика
`MaskSecret` собирается на хосте, проверяются границы 7/8/9/16 символов) и
`test_secrets_are_not_logged_verbatim` (статическая проверка, что ни одна строка с
`ESP_LOG` не печатает `serial_number_`, тело payload или `activation_challenge_`).

### P1-5. Сырые MCP-сообщения уходят в лог целиком
`main/mcp_server.cc:333` печатает `message.c_str()` при ошибке парсинга; входящее
сообщение не ограничено по длине на уровне `McpServer`.
Уточнение к плану: `max_length` в `main/mcp_server.h:115-160` применяется к аргументам
инструментов при их формировании, а не к входящим сообщениям — утверждение «в `mcp_server`
уже есть `max_length`» в плане неточно. Критерий: в лог уходит длина и первые N байт.

### P1-8. Сервер OTA по умолчанию не отвечает (задача владельцу сервиса)
`CONFIG_OTA_URL` по умолчанию — `https://ota.xiaozhi.ru/xiaozhi/ota/`. Проверка 03.10.2026
с машины разработчика: `ota.xiaozhi.ru` — DNS резолвится, но HTTPS не отвечает (порт 443
закрыт, HTTP отвечает 200). `xiaozhi.ru` в HTTPS также недоступен; `xiaozhi.me` и
`yandex.cloud` не отвечают. Вывод: с этой сети нельзя ни прошить устройство по OTA,
ни проверить сервис; часть недоступности может объясняться сетевой политикой провайдера,
поэтому требуется проверка из другой сети. Решение принимает владелец сервиса —
до него README описывает способ переопределения адреса.

### P1-9. `use_dma2d` на DSI-панелях (частично закрыто 03.10.2026)

`esp_lcd_dpi_panel_enable_dma2d()`. В коде оставались незащищённые обращения к флагу:
`main/boards/lilygo/t-display-p4/lilygo-t-display-p4.cc` и
`main/boards/m5stack/corep4/m5stack_corep4.cc`. Закрыто: оба файла переведены на схему
`#if ESP_IDF_VERSION < ESP_IDF_VERSION_VAL(6, 0, 0)` для флага плюс
`esp_lcd_dpi_panel_enable_dma2d()` для IDF ≥ 6.0 — как уже сделано в `m5stack/tab5` и
`esp32-p4-function-ev-board`. Остаточный риск перенесён в P2-11.

## 6. Вывод и порядок задач

Порядок по соотношению «риск/трудоёмкость»: P0-1 → P0-2 → P1-6 → P1-4 → P1-5 → P1-3 (зависит
от согласования протокола подписи, этап 2.3) → P1-7 (зеркала) → P2-8/P2-9/P2-11.

P0-1 и P0-2 не требуют ни серверных изменений, ни железа: правка локальная, проверяется
хост-тестом на детерминированном входе. Их следует закрыть первыми — это единственные
находки, достижимые обычным ответом сервера.

Выполнено 03.10.2026: P0-1, P0-2, P1-6, зависимость `espressif/mqtt`, перевод
`use_dma2d` на двух DSI-платах. Выполнено 04.10.2026: **P1-4** (маскирование HMAC и
серийного номера в логе, два регрессионных теста). Следующие в очереди: **P1-5**
(усечение сырых MCP-сообщений в логе), **P2-11** (защита макросов `use_dma2d` в
`main/boards/m5stack/tab5/esp_lcd_st7123.h:118` и `esp_lcd_st7121.h:130` версией IDF),
затем **P1-3** (подпись образа, зависит от согласования формата с сервером), **P1-7**
(зеркала 19 сторонних источников) и **P2-12** (полная сборка в CI или docker-образе —
локально IDF 6.0.2 и отсутствует `managed_components/`). P1-8 ждёт решения владельца
сервиса: недоступность `ota.xiaozhi.ru` может объясняться сетевой политикой провайдера,
нужна проверка из другой сети.
