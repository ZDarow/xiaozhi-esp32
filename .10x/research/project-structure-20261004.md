# Организация проекта: анализ и рекомендации

Дата: 04.10.2026
Предмет: `xiaozhi-esp32` — прошивка голосового ассистента на ESP-IDF, 177 вариантов сборки.

## Резюме

Структура репозитория в целом соответствует рекомендациям для проектов такого профиля,
и перенос её в «модную» src-layout с чистой архитектурой принёс бы больше вреда, чем
пользы. Три наблюдения, которые стоит учесть:

1. `dependencies.lock` не коммитится — сборка не воспроизводима. Это единственная
   находка из этого отчёта уровня P1.
2. `main/CMakeLists.txt` (1435 строк) содержит глобальные `GLOB` по 300 `config.json`
   и выбирает исходники плат. Любой новый файл может изменить сборку без изменения
   зависимостей — компиляция перестаёт быть инкрементальной по смыслу.
3. Отсутствует единая текстовая точка входа для типовых операций. Команда должна
   помнить точные формы флагов `scripts/build.py`; `Makefile` поверх него снял бы
   это с разработчиков и с CI.

Отдельно о процессе: до 04.10.2026 на форке не было ни одной успешной сборки.
Первая же попытка собрать прошивку вскрыла две ошибки компиляции в собственном коде
(`main/ota.cc` — незавершённый переход на `CJsonUniquePtr`; `i2c_device.cc` —
`-Werror=reorder`), которые никто не замечал, потому что сборка падала раньше, на
разрешении зависимостей. Отсутствие CI — не формальность: оно стоило двух скрытых
дефектов в ядре.

## Рекомендуемая иерархия

Изменения относительно текущего состояния — только те, что дают пользу.

```
xiaozhi-esp32/
├── main/                      # ESP-IDF компонент; имя задано build-системой
│   ├── CMakeLists.txt
│   ├── Kconfig.projbuild
│   ├── idf_component.yml
│   ├── *.cc *.h               # application, ota, settings, mcp_server, protocol
│   ├── audio/  display/  led/  notify/
│   ├── protocols/             # WebSocket + MQTT/UDP: одна абстракция, N реализаций
│   └── boards/
│       ├── common/            # переиспользуемое: сеть, кодеки, камера, BluFi
│       └── <vendor>/<board>/  # пины и config.json; ровно один DECLARE_BOARD
├── scripts/
│   ├── build.py               # каноническая точка входа сборки
│   ├── tests/                 # хост-тесты, зеркалят структуру main/
│   └── ci/                    # оверлеи конфигурации для CI
├── docs/                      # документация (актуальная)
│   └── archive/v0 v1/         # устаревшее, вне индекса поиска
├── partitions/
├── .10x/
│   ├── evidence/              # что проверено и чем
│   └── research/              # внешние обзоры и инвентаризации
├── plans/                     # планы работ
├── Makefile                   # НОВОЕ: тонкий слой над scripts/build.py
├── CMakeLists.txt
├── sdkconfig.defaults*
├── .clang-format
└── .gitignore
```

### Что предлагается изменить

| Изменение | Причина | Риск |
|-----------|---------|------|
| Добавить `Makefile` поверх `scripts/build.py` | Команда сейчас помнит точные флаги; CI, локальная сборка и docker должны вызывать одно и то же | Низкий: чистая обёртка, `build.py` не меняется |
| Перенести `docs/v0`, `docs/v1` в `docs/archive/` | Устаревшие версии засоряют поиск по документации | Низкий, но правит ссылки — нужен ревью |
| Коммитить `dependencies.lock` | Воспроизводимость сборки; сейчас версии компонентов не зафиксированы | Средний: сломает сборку, пока зеркала (P1-7) не готовы |
| Ввести `docs/adr/` для решений | Решения уровня P1-3 (подпись) сейчас живут в аудите; ADR переживут аудит | Низкий |
| НЕ переносить `main/` в `src/` | Имя компонента задаёт build-система, а не соглашение | Высокий, пользы нет |

## Обоснование

### Почему не Clean Architecture в лоб

Clean Architecture требует, чтобы зависимости смотрели внутрь: доменный слой не знает
о прошивке, адаптеры — о деталях реализации. Для прошивки ESP32 это не окупается:

- **Границы заданы аппаратно, а не архитектурой.** Проект уже отделён через интерфейс
  `Board`: ядро не знает ни о пинах, ни о конкретной плате. Это и есть требуемая
  изоляция, достигнутая тем способом, который соответствует предметной области.
- **Тестовая граница проходит по API, а не по слоям.** Из `scripts/tests` видно, что
  рабочий приём — извлечение логики из `main/ota.cc` и сборка на хосте. Слойи не нужны.
- **Изоляция внутренних слоёв не нужна.** Согласно `AGENTS.md`, ядро не использует
  внешние слои; добавлять прослойки — значит платить без выигрыша.

Материалы: `Clean Architecture 101` (Duke), `ArminasPilotas/Clean-Architecture-Notes`
(глава 28 «The Test Boundary», глава 29 «Clean Embedded Architecture»),
`Hardware-Independent Embedded Firmware Architecture Framework` (2024) — последний
прямо отмечает, что в legacy-проектах абстракция между ESP-IDF и системными функциями
отсутствовала, и именно это давало рост цикломатической сложности (среднее 3.80 против
1.05 после разделения).

### Почему зависимости должны смотреть внутрь

Направление зависимостей — единственное требование, которое здесь действительно
работает. Оно уже соблюдается:

```
main/*.cc  →  boards/common (интерфейсы)  →  boards/<vendor>/<board> (реализация)
main/*.cc  →  protocols (абстракция)     →  websocket_protocol / mqtt_protocol
```

Ядро не включает заголовки конкретных плат. Нарушение этого правила — источник
большинства будущих проблем: как только `application.cc` узнает о плате, плата
перестаёт быть заменяемой.

### Про `src/` layout

Аргумент из `packaging.python.org`: интерпретатор Python добавляет текущий каталог
в `sys.path`, поэтому «плоский» layout допускает импорт копии из рабочего каталога
вместо установленной. Для C++/ESP-IDF этого механизма нет — зависимости задаются
CMake явно. Перенос `main/` в `src/` потребовал бы переопределения
`EXTRA_COMPONENT_DIRS` и ничего бы не дал.

### Про SOLID

SOLID полезен как способ мыслить, но не как повод для иерархии папок. Из пяти
принципов здесь практически работают:

- **SRP** — виден в `main/audio/` (кодеки, движки, wake words, отладчик разделены);
- **DIP** — реализован через `Board` и `Protocol`;
- **ISP** — `ParseInt` в `main/string_utils.h` против `std::stoi` (аудит, P0-1);
- **OCP** — `MessageForLog`, `MaskSecret` добавляются без правки вызывающего кода;
- **LSP** — применим к двум реализациям транспорта.

Рефакторинг ради SOLID здесь контрпродуктивен: 177 вариантов сборки означают, что
каждое структурное изменение нужно прогонять по всей матрице.

### Про Makefile

GNU make требует объявлять не-файловые цели через `.PHONY` — иначе цель молча
перестаёт выполняться, если появится файл с таким именем. Для CI это источник
тихих пропусков. Ниже цели объявлены явно.

Makefile не заменяет `scripts/build.py`: он даёт короткие имена и единую точку входа
для CI, docker и разработчика. Согласно Nx, единая команда сборки в монорепозитории
снижает количество способов сделать одно и то же по-разному.

## Примеры конфигов

### Makefile

Тонкий слой над существующим `scripts/build.py`. Не меняет логику сборки.

```makefile
# xiaozhi-esp32 — единая точка входа для типовых операций.
# Каноническая логика сборки живёт в scripts/build.py; этот файл только называет
# типовые команды, чтобы разработчик, CI и docker вызывали одно и то же.

SHELL := /bin/bash
PYTHON ?= python3
BUILD   := $(PYTHON) scripts/build.py
OUT     := out

.DEFAULT_GOAL := help

.PHONY: help build build-p4 test test-verbose format lint clean clean-all \
        boards languages wake-words docker docker-build

help: ## Показать список целей
	@grep -hE '^[a-zA-Z_-]+:.*?## ' $(MAKEFILE_LIST) \
		| awk 'BEGIN {FS = ":.*?## "}; {printf "  \033[36m%-16s\033[0m %s\n", $$1, $$2}'

build: ## Собрать вариант по умолчанию (BOARD=путь/к/плате)
	$(BUILD) $(BOARD)

build-p4: ## Собрать вариант под ESP32-P4 (нужен IDF 6.1)
	@test -n "$(BOARD)" || { echo "Укажите BOARD=main/boards/<vendor>/<board>"; exit 1; }
	$(BUILD) $(BOARD)

test: ## Хост-тесты (C++-логика собирается на хосте, ESP-IDF не нужен)
	$(PYTHON) -m unittest discover -s scripts/tests

test-verbose: ## Хост-тесты с подробным выводом
	$(PYTHON) -m unittest discover -s scripts/tests -v

format: ## Отформатировать изменённые файлы относительно origin/main
	git diff -U0 -- '*.cc' '*.h' \
		| clang-format-diff-18 -p1 -style=file \
		| git apply -p1

lint: ## Проверить формат и YAML-конфигурацию
	@test -z "$$(git diff -U0 -- '*.cc' '*.h' \
		| clang-format-diff-18 -p1 -style=file)" \
		|| { echo "Формат не соответствует .clang-format"; exit 1; }
	yamllint .github/workflows/*.yml

boards: ## Показать список плат
	$(BUILD) --list-boards

languages: ## Показать доступные языки интерфейса
	$(BUILD) --list-languages

wake-words: ## Показать доступные модели wake word
	$(BUILD) --list-wake-words

docker: ## Собрать вариант в контейнере (BOARD_DIR=vendor/board, BOARD_NAME=имя)
	@test -n "$(BOARD_DIR)" || { echo "Укажите BOARD_DIR=vendor/board"; exit 1; }
	docker run --rm \
		-e FIRMWARE_BOARD_DIR=$(BOARD_DIR) \
		-e FIRMWARE_BOARD_NAME=$(BOARD_NAME) \
		-e FIRMWARE_LANGUAGE=$(or $(LANG),zh-CN) \
		-v "$(CURDIR)/$(OUT):/output" \
		xiaozhi-builder

docker-build: ## Собрать образ сборщика
	docker build --build-arg FIRMWARE_SOURCE_REVISION="$$(git rev-parse HEAD)" \
		-f docker/firmware-builder/Dockerfile -t xiaozhi-builder .

clean: ## Удалить локальный каталог сборки
	rm -rf build

clean-all: clean ## Удалить каталог сборки и загруженные компоненты
	rm -rf managed_components components out
```

Обратите внимание: `build` требует `BOARD=`. Пустое значение должно давать понятную
ошибку, а не молча собирать что-то одно — поэтому проверка через `test -n` стоит
перед командой, а не после.

### .gitignore

Текущий файл уже покрывает сгенерированные каталоги ESP-IDF. Ниже — вариант с
явным разделением по причинам и с защитой секретов.

```gitignore
# ── Сгенерированное сборкой ESP-IDF ────────────────────────────────
# Всё это пересоздаётся командой scripts/build.py, в git не нужно.
/build/
/managed_components/
/components/
/sdkconfig
/sdkconfig.old
/dependencies.lock

# ── Секреты ───────────────────────────────────────────────────────
# Приватный ключ подписи OTA не должен попасть в репозиторий ни при каких
# условиях: подписанный образ без возможности выпуска новой версии — ловушка.
*.pem
*.key
*.p12
*.crt
.env
.env.local
secrets.*

# ── Локальное окружение ───────────────────────────────────────────
# Настройки VS Code содержат абсолютный путь к ESP-IDF на конкретной машине.
/.vscode/*
!/.vscode/extensions.json
/.clangd
/.cache
/devcontainer/
__pycache__/
*.pyc

# ── Артефакты сборки ──────────────────────────────────────────────
/out/
/dist/
/releases/
/tmp/
*.bin
mmap_generate_*.h
/main/assets/lang_config.h

# ── Прочее ────────────────────────────────────────────────────────
.DS_Store
```

Разница с текущим файлом — четыре содержательных пункта:

1. **Якоря `/build/` вместо `build/`.** Без ведущего слэша правило применяется к
   каталогу `build` в любом месте дерева, включая вложенные. Для ESP-IDF каталог
   сборки всегда один и он в корне, поэтому `/build/` точнее.
2. **Явные расширения ключей.** Текущий файл игнорирует только `.env`; расширения
   добавляют защиту от типичной ошибки с `signing_key.pem`.
3. **Ветка `/out/`.** Каталог, куда docker-контейнер пишет артефакты через volume.
   Проверено на практике: после неудачной сборки там остались `build.log` и
   `manifest.json`, которые не должны попасть в индекс.

Секреты под разделением, а не в общем списке — потому что это единственное правило,
нарушение которого нельзя исправить откатом коммита: ключ, попавший в историю,
остаётся в клонах.

### Про lock-файл: почему это не формальность

Выше `dependencies.lock` оставлен в игнорируемых вместе с `build/` и
`managed_components/`. Это решение апстрима, и менять его нужно вместе с зеркалами,
но основания стоит проговорить отдельно.

Проверка 04.10.2026 показала, чего стоит отсутствие `dependencies.lock` в индексе.
Сборка падала на этапе version solving из-за зависимости, которой нет ни на GitHub,
ни в реестре, и ничто в репозитории этого не отражало: манифест выглядел корректно,
а проект не собирался ни на одной из 177 плат. Обнаружить это можно было только
запуском сборки.

Lock-файл решает и обратную задачу: он фиксирует проверенное состояние, поэтому
«плавал» только бы явно — обновление видно в диффе, а не проявляется как
необъяснимый сбой сборки спустя месяцы.

Вторая половина того же аргумента — провенанс. Сторонние компоненты тянутся с
GitHub, где нет ни тегов, ни гарантий совместимости с целевым SDK. Сборка 04.10.2026
показала обе проблемы за один прогон: несуществующий форк и компонент, не
совместимый с IDF 6.1. Ни одна из них не видна в манифесте — обе обнаружились
только компиляцией. Пока компоненты сторонние и версии их транзитивных
зависимостей не зафиксированы, «собралось у меня» не означает «соберётся в CI».

## Чек-лист готовности к масштабированию и CI/CD

### Воспроизводимость сборки

- [x] Проверена доступность всех сторонних источников `main/idf_component.yml`
      (04.10.2026). Из 19 сторонних компонентов 9 отдают 404 на GitHub, но
      успешно разрешаются через реестр ESP — там они зарегистрированы под теми же
      именами. Проверять нужно реестр, а не GitHub.
- [ ] **Ошибка в зависимости (исправлено 04.10.2026):** в `main/idf_component.yml`
      был указан `ZDarow/xiaozhi-fonts`, форк которого никогда не был создан — 404 и на
      GitHub, и в реестре. Сборка падала на этапе version solving для **любой** платы.
      Заменено на `78/xiaozhi-fonts: ~2.0.0` (версия 2.0.0 есть в реестре).
      Комментарий в манифесте объясняет, что возврат к форку — только после его
      создания. Этот класс ошибок — главный аргумент за коммит lock-файла: с ним
      такое расхождение обнаруживается на первой же сборке.
- [ ] **Вендорный компонент несовместим с целевым SDK (не исправлено 04.10.2026):**
      `78/uart-uhci` 0.3.3 использует `gdma_get_alignment_constraints`, удалённый в
      IDF 6.1. Компонент подключается только для `target not in [esp32]`, поэтому
      чистый `esp32` собирается, а остальные цели — нет. В реестре есть 0.4.0, но его
      тянет `78/uart-eth-modem` 0.6.5; обновление последнего до 0.7.0 не провере-
      но и затрагивает платы с UART-Ethernet. Решение — за владельцем.
      Подробности в `.10x/evidence/audit-20261003.md` (P1-11).
- [ ] Коммитить `dependencies.lock` (`build/` и `managed_components/` — в `.gitignore`).
      Сейчас 65 зависимостей не зафиксированы версиями: сборка 03.10 и 04.10 может
      дать разный результат. Блокируется зеркалами (P1-7).
- [ ] Зафиксировать точные версии для компонентов с диапазонами (`78/esp-ml307 ~3.7.0`
      → точная версия).
- [ ] Проверка в CI, что lock-файл согласован: `git diff --exit-code dependencies.lock`
      после сборки. Сбой означает, что версия уплыла.
- [ ] Решить, коммитится ли `sdkconfig.defaults.<target>`. Сейчас коммитятся, и это
      правильно: дефолты — часть контракта сборки.

      концентрируются вокруг входа от сервера — это осознанный выбор, но не полный
      показатель.
- [ ] Каждая находка аудита получает регрессию. Требование выполнено для P0-1,

      падают при откате правки.
- [ ] Тест на каждую плату не нужен и невозможен: 177 вариантов. Вместо этого —
      матрица на репрезентативные чипы (`esp32`, `esp32s3`, `esp32c3`, `esp32p4`).
- [ ] CI прогоняет тесты до сборки — уже так, это правильный порядок: дешёвая проверка
      перед дорогой.

### CI/CD

- [ ] `fail-fast: false` в матрице — уже стоит, иначе одна упавшая плата скрывает
      остальные.
- [ ] Кэш ccache между прогонами. В docker-образе `-DCCACHE_ENABLE=True` уже включён,
      но кэш не переиспользуется между job'ами: каждый из 177 вариантов компилирует
      ESP-IDF заново. Это главное место для ускорения.
- [ ] Таймауты на job'ах. Сейчас не заданы: зависшая сборка будет висеть до лимита
      GitHub Actions.
- [ ] Матрица растёт линейно с числом вариантов. `--select-changed` для PR решает
      это для разработки, но на push в `main` собираются все 177.
- [ ] Артефакты именуются с `github.sha` — уже так, верно.
- [ ] Отдельный job для быстрых проверок (линт, формат, тесты) не должен ждать
      матрицы: сейчас `prepare` — отдельный job, это правильно.

### Структура

- [ ] `main/CMakeLists.txt` (1435 строк) — кандидат на разбиение. Глобальные `GLOB`
      означают, что новый файл меняет сборку без изменения зависимостей: инкрементальность
      сохраняется на уровне CMake, но теряется на уровне смысла «я изменил этот файл».
- [ ] `main/boards/common/` (36 файлов) — на грани. При росте плат имеет смысл
      разделить на `network/`, `codecs/`, `camera/`, `provisioning/`.
- [ ] Решения уровня P1-3 оформить как ADR в `docs/adr/`. Подпись образа затрагивает
      сервер, клиент и выпуск — это решение переживёт аудит.
- [ ] `docs/v0`, `docs/v1` — перенести в `docs/archive/`, чтобы поиск по документации
      не выдавал устаревшее.
- [ ] `main/Kconfig.projbuild` (1191 строка) — растёт монотонно. Делить по платам
      рано: связь с `config.json` важнее, чем размер файла.

### Уникальность идентичности платы

- [x] Проверено 04.10.2026: имя платы (`board_name`) и тип (`type`) для OTA берутся из
      `config.json`, а не из имени каталога. Это правильно — совпадение имён не
      гарантировано, например `espressif/esp32-s3-box-3` даёт `type: esp-box-3`.
- [ ] Ветка совместимости при добавлении платы. По правилам проекта идентичность
      платы влияет на совместимость OTA: переименование `type` у существующей платы
      ломает обновление у пользователей. Требуется проверка в `scripts/build.py`,
      что `type` не переиспользуется.

### Сборочная среда

- [ ] Локальный IDF (6.0.2) и CI-образ (6.1) различаются, и P4/S31 собираются только
      в CI. Расхождение не зафиксировано в коде: агент узнаёт о нём только из
      `AGENTS.md`. Стоит добавить проверку версии IDF в `scripts/build.py` с понятной
      диагностикой, а не полагаться на документ.
- [ ] Docker-образ сборщика — воспроизводимый путь обхода этого ограничения.
      Проверено 04.10.2026: образ работает и плата `waveshare/esp32-touch-lcd-3.5`
      (чистый `esp32`) собирается полностью — 0 ошибок, 0 предупреждений, артефакты с
      sha256 в `.10x/evidence/`. Плата `esp32s3` проходит конфигурацию, но падает на
      несовместимости стороннего `78/uart-uhci` с IDF 6.1 (P1-11) — это код вендора,
      а не форка.

### Владение и процесс

- [ ] `AGENTS.md` описывает правила для агентов и уже служит источником правды о
      статусе находок. Отдельный `CONTRIBUTING.md` существует.
- [ ] Каталог `.10x/` нестандартен для апстрима и будет конфликтовать при синхронизации
